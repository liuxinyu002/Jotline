让「可执行契约」先于一切业务代码存在

Jotline 是一个本地优先的记录型应用（Tauri + Rust 主进程 + 前端 + LLM sidecar）。Phase-1 不写任何业务功能——它建立的是三轨并行开发的公共地基：单一契约源、机械生成管线、语义 Mock、CI 防漂移闭环。

01

背景

Phase-1 之前仓库里只有文档（PRD v2.1 / SPEC v0.7 / Roadmap），没有一行代码。这个 change 要回答的问题是：三个团队（后端、Agent、前端）即将并行开工，如何保证他们对「接口」的理解在三个月后仍然一致？

项目处于什么阶段

Jotline 的整体架构是 Tauri 桌面应用：Rust 主进程持有 SQLite 与文件库，对外暴露 localhost HTTP 领域 API（127.0.0.1:4765）；前端（主窗 + 浮窗）消费这些 API 并通过 SSE 订阅变更；LLM sidecar 经 stdio JSON-RPC 与主进程通信。SPEC 已经冻结了大量协议决策（ADR-1~13），Roadmap 把开发切成了 20 个 Phase，其中 Phase-2 起 BE-Core / BE-Agent / FE 三轨并行。

并行意味着风险：后端改了一个字段名，前端和 Agent 轨不知道；前端按想象中的接口写了代码，联调时才发现两边的「契约」从来不是同一份。Roadmap 把它列为头号风险——契约漂移。

Phase-1 的定位

传统项目的对策是「写一份 API 文档，大家遵守」——靠纪律。这个 change 的对策是把契约变成可执行的机器产物：接口定义只存在一处（Rust 契约源），三端消费物全部由它机械生成，生成物提交入库，CI 用 git diff 检查——改了源而不重新生成，物理上无法合入。文档会撒谎，diff 不会。

这个 change 交付了什么

  • monorepo 骨架：pnpm workspace（app / sidecar / contracts/mock / contracts/generated）+ Rust 虚拟 Cargo workspace + 工具链版本钉死 + Biome + README 本地开发节。
  • Rust 契约源 crate（src-tauri/crates/contracts，零 tauri 依赖）：78 个 Schema 类型覆盖鉴权/错误/笔记/SSE/stdio JSON-RPC/实体/捕获八个域，20 个路径以 utoipa 注解 stub 承载。
  • 生成管线：cargo run --bin gen 产出 openapi.json 与自包含工具 Schema；openapi-typescript 产出 @jotline/contracts TS 类型包。
  • 协议文档 contracts/PROTOCOL.md：Wire 纪律、错误码表、鉴权约定、SSE 事件注册表、JSON-RPC 方法注册表、15 个 ID 前缀。
  • 契约 Mock 服务：语义内核（内存状态 + SSE 广播 + 心跳）+ 剧本层（延迟/错误注入）+ 4 个场景数据集。
  • CI 布防：GitHub Actions 三 job + pre-commit hook + main 分支 required check。

为什么「现在」做

三个理由决定了时序不可交换：其一，Phase-2 的最小垂直切片立即消费契约类型与 stdio 协议——没有地基，切片无从开工；其二，双轨并行一旦启动，防漂移机制必须已经在位，事后补建意味着漂移已经发生；其三，前端轨到 Phase-11 才需要真实联调，但那时后端未必就绪——Mock 服务让前端在第一天就有可用的「后端」。

02

直觉

这一节讲设计判断：四个关键决策各自的「为什么」，以及藏在生成器里那个最容易被忽略的 quirk。

核心机制：一条单向管线 + 一个闭环 防漂移

整个 change 的骨架是一条单向数据流：Rust 契约源是唯一的「源」，其余一切都是「产物」。产物不允许手写、不允许手改——因为能手写的东西就会有第二份、第三份，然后漂移。

决策一：契约源住在哪里 D1

第一道题看似琐碎，实则卡在「冻结」上。SPEC §3.2 已冻结五目录结构，其中 contracts/ 的描述是「CI 生成物」——把 Rust 源码放进去，目录语义自相矛盾；在顶层新增一个 crates/ 目录，等于给冻结结构加第六目录，程序上需要先修 ADR。唯一合规解：源住在 Rust workspace 内部但不占 contracts/——根虚拟 Cargo manifest 把 src-tauri/crates/contracts 挂为 member。附带一条纪律：这个 crate 零 tauri 依赖（只依赖 utoipa / serde / chrono / ulid），保证 Linux CI 上秒级编译，不需要装任何平台工具链。

决策二：一条管线覆盖三种「线上形态」 D3

项目的线上协议不止 HTTP：SSE 事件流有自己的信封，主进程 ↔ sidecar 走 stdio JSON-RPC，Agent 工具调用需要 JSON Schema。 naive 做法是给每种形态配一条类型链（比如再用 ts-rs 生成一份 Rust→TS）——但每多一条链就多一套工具、多一份漂移面。

这个 change 的选择是全部塞进 OpenAPI components：SSE 信封（StreamEnvelope）与 JSON-RPC 消息（Ipc*）即使没有任何 path 引用它们，也注册进 components——openapi-typescript 会为全部 components 生成 TS 类型，于是 HTTP、SSE、stdio 三种形态共用同一条生成链。代价是 openapi.json 里混入了「非 HTTP 类型」这一 quirk，在 PROTOCOL.md 显式文档化。工具 Schema 则由 gen bin 在生成期把 $ref 解引用展开成自包含 JSON Schema 写入 contracts/tools/——因为消费方（Phase-8/9 的 LLM 工具调用）拿到的是单个独立文件，内含未解析的外部引用就没法用。

决策三：Wire 纪律机械化 D4

三端共享协议最怕「语义含糊」。SPEC 冻结了一组 Wire 纪律，这个 change 的任务是让每条纪律都有机器保证而不是 code review 肉眼：

时间 = RFC 3339 UTCTimestamp newtype（chrono DateTime<Utc>）Schema format: date-time；带偏移输入归一化为 Z 后缀

生成器里的 quirk：null 剔除 S2

整条管线最微妙的一步藏在 gen bin 里。utoipa 对 Rust Option<T> 生成的 OpenAPI 形态是「可空联合」——oneOf: [{type: "null"}, X] 或 type: [T, "null"]。openapi-typescript 忠实地把它翻译成 field?: X | null。这与 Wire 纪律「可选 = 字段省略，禁 required-nullable」正面冲突：

✗ utoipa 原生产物
target_dir?: string | null
消费方必须同时处理「字段不存在」和「字段是 null」两种缺省形态——这正是纪律要消灭的歧义。
✓ null 剔除后
target_dir?: string
缺省只有一种表达：字段省略。Rust 侧 skip_serializing_if 保证序列化时确实省略，两端语义对齐。

解决位置不在类型标注层，而在生成期后处理：gen bin 把整个文档转成 serde_json::Value 后递归剔除 null 形态（strip_null），查询参数剔 null 后还要把 required: true 修正为 false。选择在这里修而不是换掉 utoipa，是因为剔除规则只有一处、可被「两次生成零 diff」与 TS typecheck 双重验证——修在几十个字段标注上则每个都可能漏。

决策四：Mock 为什么是「语义」的 D5

Mock 服务有两种经典形态。剧本式：每个路由返回硬编码响应，写起来快，但 Roadmap Phase-11 有个验证——「窗口 A 创建笔记，窗口 B 刷新后可见，双窗一致」。剧本式结构上做不到：要让窗口 B「看到」窗口 A 的写操作，Mock 必须真的维护状态、真的把变更推给 SSE 订阅者；若用剧本模拟，每个场景都要手写一份 SSE 时序，等于在 Mock 里手写第二份领域语义。

所以这个 Mock 有一个语义内核：内存状态由场景文件播种，写操作（create/upsert/execute）真实变更状态并广播 SSE 事件，读操作反映变更后的状态；其上叠一层剧本覆写（延迟注入、错误注入、预定义事件序列），剧本优先于语义。边界被明确钳制：语义只覆盖契约域内实体（projects / notes / todos / cards 等）的基础读写，不实现任何业务规则（推断、聚合、降级）——Mock 越像真后端就越难维护，FE 阶段需求超出时先补场景文件而非扩引擎。

为什么 Mock 自己读 openapi.json 来定路由

Mock 的路由表不是手写的——启动时读生成的 openapi.json 编译成正则路由。效果：契约里没有的路由，Mock 物理上不存在（404 信封）；契约新增路由后 Mock 自动「长」出来（未实现的 operation 会显式报错而非静默）。Mock 与真实主进程共享同一份契约定义，前端对着 Mock 调通的行为就是对着真后端的行为。

没有被采纳的方案

  • tauri-specta（IPC 类型生成）——不采纳（D6）：DEC-01 关闭后 IPC 面只剩系统能力（tauri-plugin 官方自带类型），自定义 command 趋近于零——生成器没有可生成的面。按 SPEC 自身决策程序以 IDR-01 定稿，SPEC §3.2 工具链行同步修订。
  • ts-rs 第二条 TS 生成链：为 SSE / JSON-RPC 单独建链会多一份工具维护成本与漂移面，被「全部并入 components」替代（D3）。
  • utoipa-cli 直接输出：做不到工具 Schema 的 $ref 解引用、多文件写出与键排序控制，改为 crate 内自写 gen.rs。

ID 基座：宏 + 前缀注册表

15 个实体的 ID 类型由同一个宏生成。每个 newtype 都是字符串包装，但反序列化时校验前缀与 ULID 格式（Crockford Base32，26 字符，去 I L O U），Schema 层带 pattern 正则——同一份约束同时活在三处：Rust 解析、JSON Schema 校验、Mock 场景校验。

src-tauri/crates/contracts/src/ids.rs节选
/// ULID 主体的正则片段（Crockford Base32）。
pub const ULID_BODY: &str = "[0-9A-HJKMNP-TV-Z]{26}";

macro_rules! define_id {
    ($name:ident, $prefix:literal) => {
        #[derive(…, Serialize)]
        #[serde(transparent)]
        pub struct $name(String);

        impl $name {
            pub const PREFIX: &str = $prefix;
            /// 从完整 ID 字符串解析（校验前缀与 ULID 格式）。
            pub fn parse(raw: &str) -> Result<Self, String> { … }
        }

        impl<'de> Deserialize<'de> for $name { // 反序列化即校验
            fn deserialize<D: Deserializer<'de>>(d: D) -> Result<Self, D::Error> {
                let raw = String::deserialize(d)?;
                $name::parse(&raw).map_err(serde::de::Error::custom)
            }
        }

        impl PartialSchema for $name { // Schema 带 pattern 正则
            fn schema() -> RefOr<Schema> {
                ObjectBuilder::new()
                    .schema_type(Type::String)
                    .pattern(Some(concat!("^", $prefix, "_", "[0-9A-HJKMNP-TV-Z]{26}$")))
                    .into()
            }
        }
    };
}

域类型：标注即文档

以创建笔记请求为例，一个结构体同时是：serde 序列化目标、utoipa Schema 来源、TS 类型的祖先。注意可选字段的组合拳——#[serde(default, skip_serializing_if)] 保证 Wire 上「无值即省略」，null 剔除保证 TS 侧无 | null。检索响应 SearchHit 则逐字段对齐 SPEC §5 的冻结承诺（id / title / snippet / provenance / score）。

/// 创建笔记请求。
#[derive(…, Serialize, Deserialize, ToSchema)]
pub struct CreateNoteRequest {
    pub project_id: ProjectId,
    pub title: String,
    pub body: String,
    /// 目标目录（单归属；缺省落模板默认目录）
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub target_dir: Option<String>,
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub tags: Option<Vec<String>>,
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub format: Option<NoteFormat>,
}

    post,
    path = "/api/notes",
    tag = "notes",

    responses(

「stub」是 Phase-1 的临时形态：没有 handler 可挂注解，就让空函数承载 #[utoipa::path]。迁移正确性的证明方式很优雅——注解内容不变则 openapi.json 零 diff，diff 就是迁移没有引入漂移的证据。捕获域还有一个 spike S1 验证过的细节：卡片内容 tagged enum 的判别值是带点号的 "card.batch"（#[serde(rename = "card.batch")]），serde 与 TS union 都正确处理。

生成器：确定性与两个后处理

gen.rs 只做三件事：组装 ApiDoc、剔除 null 形态、解引用工具 Schema 的 $ref。确定性来自一个不起眼的选择——先转成 serde_json::Value 再序列化：Value 的 map 是 BTreeMap，全层级键按字典序排序，加上无时间戳无随机内容，同源两次运行字节一致，CI diff 检查因此成立。

/// Wire 纪律机械化（spike S2 结论落地）：utoipa 对 Option<T> 生成「可空联合」
/// （oneOf: [{type: null}, X] 或 type: [T, null]），与本库 Wire 纪律冲突——
/// 生成期统一剔除 null 形态。
fn strip_null(value: &mut serde_json::Value) -> bool {
    match value {
        serde_json::Value::Object(map) => {
            // oneOf: [{type: "null"}, X] → X（X 的键提升到当前层级）
            if let Some(serde_json::Value::Array(variants)) = map.get_mut("oneOf") {
                if variants.len() == 2 && variants[0] == serde_json::json!({"type": "null"}) {
                    let x = variants.remove(1);
                    map.remove("oneOf");
                    if let serde_json::Value::Object(xm) = x {
                        for (k, v) in xm { map.insert(k, v); }
                    }
                }
            }
            // type: [T, "null"] → 去除 "null"；单一元素坍缩为标量

        }
        …
    }
}

async handle(req, res): Promise<void> {
    const url = new URL(req.url ?? "/", "http://127.0.0.1");
    const method = (req.method ?? "GET").toLowerCase();

    // 控制端点（不在 openapi.json，非契约面）
    if (url.pathname.startsWith("/_mock/")) { this.handleControl(method, url, res); return; }

    // 契约路由匹配（契约外 404）
    const route = this.routes.find((r) => r.method === method && r.regex.test(url.pathname));
    if (!route) { this.sendJson(res, 404, errorEnvelope("not_found", `契约外路由：…`)); return; }

    // Bearer 鉴权（错 token 401 错误信封）
    if (req.headers.authorization !== `Bearer ${DEV_TOKEN}`) {
        this.sendJson(res, 401, errorEnvelope("unauthorized", "未携带或错误的 Bearer token…"));
        return;
    }

    // 场景选择：请求级（X-Mock-Scenario，仅剧本生效）→ 否则全局激活场景
    let scenarioName = this.activeScenario;
    const headerScenario = req.headers["x-mock-scenario"];
    …

    // 剧本层（优先于语义内核的默认行为）：延迟注入 / 错误注入
    const script = this.routeScript(scenario, route, url.pathname);
    if (script?.delay_ms) await sleep(script.delay_ms);
    if (script?.error) { this.sendJson(res, script.error.status, …); return; }

    // SSE：剧本流（预定义事件序列）或常驻订阅（广播 + 心跳）
    if (route.operation.operationId === "get_stream") { … return; }

    // 请求体：按契约 Schema 校验（违反契约 → 422 信封含字段定位，状态不变）
    const bodyValidator = this.validator.requestBodyValidator(route.operation);
    if (bodyValidator) {
        body = await readJsonBody(req);
        if (!bodyValidator(body)) {
            this.sendJson(res, 422, validationEnvelope("请求体校验失败", …));
            return;
        }
    }

    // 语义分发：按 operationId 落到语义内核
    const result = this.dispatch(route, pathParams, query, body);
